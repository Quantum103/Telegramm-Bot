# Доставка входящих Telegram updates

## Решение этапа 6.2

**Отдельную таблицу Durable Inbox не добавляем.** Для текущего long polling достаточно механизма подтверждения Telegram через `getUpdates(offset)`, если приложение строго соблюдает правило: повышает offset только после успешной обработки update.

Это решение не означает, что обработка уже безошибочна. Сейчас часть обработчиков возвращает успешный результат даже после внутренних ошибок. Это отдельный дефект, который должен быть устранён на этапе 6.3 до подключения worker pool.

## Почему отдельная inbox-таблица не нужна

Telegram хранит входящие updates на своей стороне до подтверждения. Update считается подтверждённым, когда приложение вызывает `getUpdates` с offset, который больше `update_id` этого события. При запросе без продвижения offset Telegram возвращает самое раннее неподтверждённое событие и последующие события.

Следствия для приложения:

- Полученный update нельзя считать подтверждённым только потому, что HTTP-ответ `getUpdates` получен или событие поставлено в локальную очередь.
- После успешной обработки update следующий запрос может использовать `offset = update_id + 1`.
- При временной ошибке offset не меняется. Следующий запрос повторно получает неподтверждённый update.
- После перезапуска процесс начинает polling с начального offset. Уже подтверждённые события Telegram повторно не отдаёт, а неподтверждённые снова доступны.
- Если ответ на `getUpdates` потерян или процесс аварийно завершился до следующего подтверждающего запроса, тот же offset позволяет получить неподтверждённые updates повторно.

Таким образом, локальная таблица, дублирующая очередь Telegram до момента подтверждения, не добавляет необходимой гарантии для текущей схемы.

## Ограничение гарантии

Telegram хранит updates **не более 24 часов**. Если бот не получает событие в течение этого периода, собственная inbox-таблица приложения не сможет его восстановить: приложение ещё не успело сохранить событие у себя.

Inbox потребуется пересмотреть, если приложение будет подтверждать updates сразу после их долговременной записи в PostgreSQL и обрабатывать их независимо от Telegram, если появится несколько конкурирующих poller-процессов или если понадобится собственное хранение уже полученных событий.

## Обязательные инварианты для worker pool

После перехода на параллельную обработку сохраняются следующие правила:

1. Получение batch и постановка update в очередь не двигают offset.
2. Offset продвигается только через непрерывный префикс успешно завершённых updates.
3. Если update с меньшим `update_id` завершился временной ошибкой, offset не может перескочить через него, даже если более поздние updates уже завершились.
4. После повторной выдачи batch уже успешно обработанные более поздние updates могут встретиться повторно. Их бизнес-эффекты должны быть идемпотентными.
5. При остановке приложения незавершённые updates остаются неподтверждёнными и должны быть получены повторно после перезапуска.
6. Ошибки обработчиков нельзя маскировать как успешную обработку. Постоянно некорректное или неподдерживаемое событие должно иметь отдельную явную политику завершения, а не бесконечно блокировать очередь.

В текущем последовательном `Bot.Run()` offset уже локальный и увеличивается после `handleUpdate() == true`. Это правильная базовая модель. Однако callback-обработчики и часть текстовых/командных обработчиков пока не всегда передают ошибки обратно в `handleUpdate()`; это будет исправлено отдельно на этапе 6.3.

## Что проверяется тестами

Этап 6.2 добавляет регрессионную проверку: если обработчик текстового update получает временную ошибку при проверке режима диалога, следующий вызов `getUpdates` должен прийти с тем же offset. Тест подтверждает, что событие не подтверждается преждевременно.

## Итог

- Новая таблица и миграция не нужны.
- Источник повторной доставки до подтверждения — Telegram.
- Локальный offset не требуется сохранять в PostgreSQL.
- Главные условия надёжности — достоверный результат обработчика, идемпотентность и непрерывный watermark при параллельной обработке.

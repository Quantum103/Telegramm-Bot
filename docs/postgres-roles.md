# PostgreSQL: разделение учётных записей

Compose использует три отдельные роли:

| Роль | Назначение | Права |
|---|---|---|
| `bible_app` | исходная административная роль образа PostgreSQL | суперпользователь; используется только при инициализации/настройке |
| `bible_runtime` | backend приложения | `SELECT`, `INSERT`, `UPDATE`, `DELETE` на таблицах, `USAGE/SELECT` на последовательностях; без DDL и управления ролями |
| `bible_migrator` | `golang-migrate` | владелец прикладной БД и схемы `public`, может применять миграции; не суперпользователь |

Backend не получает пароль `POSTGRES_PASSWORD`. Он подключается только как `bible_runtime`. Миграции запускаются как `bible_migrator`.

## Настройка

В `.env` задай независимые длинные случайные значения для:

- `POSTGRES_PASSWORD` — административная учётная запись;
- `DATABASE_PASSWORD` — `bible_runtime`;
- `MIGRATIONS_PASSWORD` — `bible_migrator`.

Для пароля мигратора, который входит в URI подключения, используй URI-safe пароль (буквы/цифры, `_`, `-`) либо задай `MIGRATIONS_DATABASE_URL` с percent-encoded паролем.

**Для существующего Docker volume не меняй `POSTGRES_USER` и `POSTGRES_PASSWORD` наугад.** Они должны совпадать с исходной административной учётной записью volume. Простая смена этих переменных не меняет уже созданные PostgreSQL-роли.

## Применение к существующей базе

1. Сделай проверенную резервную копию. Пример для локального Compose:

   ```bash
   docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > postgres-before-role-split.sql
   ```

2. Обнови проект и `.env` с тремя разными паролями.
3. Запусти PostgreSQL и настройку ролей:

   ```bash
   docker compose up -d postgres db-roles
   docker compose logs db-roles
   ```

4. Примени неприменённые миграции отдельной командой:

   ```bash
   docker compose --profile tools run --rm migrate
   ```

5. Запусти приложение:

   ```bash
   docker compose up --build -d
   ```

Сервис `db-roles` выполняется после готовности PostgreSQL. Он идемпотентно создаёт/обновляет роли, передаёт `bible_migrator` владение объектами текущей прикладной базы и выдаёт `bible_runtime` необходимые права. SQL-скрипт не удаляет таблицы и строки. Если роль исходного администратора не совпадает с `POSTGRES_USER` в `.env`, остановись и сначала восстанови правильные учётные данные — не пытайся запускать provisioning наугад.

## Проверка результата

Backend должен подключаться к БД как `bible_runtime`, мигратор — как `bible_migrator`. У runtime-роли должны быть права чтения/изменения прикладных данных и не должно быть права `CREATE` на схему `public`. CI проверяет, что runtime не является суперпользователем, не может создавать таблицы и имеет необходимые DML-права.

Эта настройка уменьшает последствия компрометации backend, но не защищает от всех атак и не заменяет резервные копии, контроль доступа к Docker-хосту, TLS и независимое тестирование безопасности.

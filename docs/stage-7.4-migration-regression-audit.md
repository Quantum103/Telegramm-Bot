## 2. Upgrade test: схема v11 → текущая v15

Сценарий выполняется на отдельной базе `bible_platform_upgrade_test`, не на базе, используемой обычными интеграционными тестами.

### Последовательность

1. Создаётся новая пустая БД.
2. `migrate goto 11` применяет миграции 1–11.
3. В схеме v11 создаются исторические данные двух учеников, курсы, уроки, опубликованные версии, вопросы, прохождения и один сохранённый ответ.
4. `migrate goto 13` применяет миграции 12 и 13.
5. На версии 13 добавляется длинный реферальный код старого формата.
6. `migrate up` применяет миграции 14 и 15.
7. SQL assertions проверяют сохранность и преобразование исторических данных, а также работоспособность новой таблицы очереди Telegraph.

### Сценарий A: однозначная история ученика

До обновления в v11 создаётся ученик с одним незавершённым прохождением урока, который состоит ровно в одном курсе. Для прохождения заданы текущий вопрос и сохранённый текстовый ответ.

После обновления проверяется:

- ученик и курс остались в БД;
- создано прохождение курса с `run_number = 1`, `mode = ai`, `status = in_progress`;
- создан снимок обязательных уроков в `course_enrollment_lessons`;
- старое `lesson_enrollments` связано с новым `course_enrollment`;
- `current_question_id`, версия урока и ранее сохранённый текстовый ответ сохранились.

Это проверяет фактический data backfill миграции `000012_course_enrollments`, а не только создание её таблиц.

### Сценарий B: неоднозначная история

Второй ученик имеет незавершённое прохождение урока, который одновременно входит в два разных курса.

Миграция не должна выбирать курс наугад. Assertions подтверждают, что:

- для ученика не создаётся автоматически `course_enrollment`;
- исходная строка `lesson_enrollments` остаётся в БД;
- её `course_enrollment_id` остаётся `NULL`;
- статус и текущий вопрос сохраняются.

Это защищает от ложного назначения исторического прогресса в неверный курс.

### Сценарий C: реферальный код сотрудника

На версии 13 создаётся код старого формата `c_` плюс 43 символа. После миграции `000014_simple_staff_referral_codes` проверяется:

- старое значение сохранено в `legacy_code`;
- новое значение имеет формат `c_<staff_id>`;
- новая колонка содержит уникальный короткий код сотрудника.

### Сценарий D: последняя миграция

После `000015_bible_chapter_telegraph_jobs` проверяется наличие таблицы `bible_chapter_telegraph_jobs` и вставка валидной queued-задачи. Тем самым проверяется не только версия схемы, но и базовые ограничения новой таблицы очереди.

### Race detector

Проверка расширена с одного пакета Telegram до всех backend-пакетов:

```bash
cd backend
go test -race ./...
```

В первом общем запуске race-suite сами интеграционные тесты обнаружили проблемы повторяемости тестовых данных:

- Redis login limiter использовал один фиксированный IP между независимыми запусками, поэтому накопленный failure counter блокировал следующую проверку.
- Два теста Telegram-привязки использовали постоянные SHA-256 токены, которые уже оставались в тестовой БД после предыдущего запуска.

Это были конфликты тестовых данных, не сообщения `WARNING: DATA RACE`. Исправлено:

- `uniqueLimiterIdentity` генерирует отдельный тестовый IP и email;
- тесты Telegram-привязки генерируют уникальный hash для каждого запуска.

После этих исправлений `go test -race ./...` прошёл успешно на CI №836.

## 6. Границы проверки

- Upgrade test использует синтетические данные на схеме v11 и проверяет переход по фактическим SQL-миграциям до v15. Это не заменяет проверку восстановления реальной production-копии.
- Проверялась PostgreSQL 18 из CI.
- Тест не использует персональные данные учеников и не подключается к production БД.
- В этом этапе production handlers и сами SQL migrations не менялись; изменения относятся к тестам, CI и документации.

Для реального обновления production перед применением миграций всё равно требуется отдельная резервная копия и проверка восстановления этой копии.

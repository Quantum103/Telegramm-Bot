# Оптимизация навигации по вопросам

## Что изменилось

- Telegram callback больше не вызывает `GetProgress` отдельно перед `NextQuestion`/`PreviousQuestion`. Для production LearningService используется единая операция `NavigateFromQuestion`.
- Сервис в одном проходе проверяет активного ученика, принадлежность прохождения ученику, активный запуск курса и привязку неизменяемой версии урока; определяет соседний вопрос; условно сохраняет новую позицию; загружает сохранённый ответ и последнюю попытку.
- Условное обновление позиции сравнивает `current_question_id` с вопросом, для которого была нажата кнопка. Повторный или устаревший callback не перезаписывает актуальную позицию.
- Проверка запуска курса/ученика/режима/lesson_version_id выполняется одним `EXISTS` запросом вместо двух отдельных чтений.
- `showQuestion` использует `OpenCurrentQuestion`, поэтому восстановление экрана не делает сначала отдельный `GetProgress`, затем второй `OpenQuestion`.
- Для заголовка экрана используется `CatalogService.GetLesson`; production-вызов не загружает весь `LessonDetail`.
- `ListQuestionsForVersion` использует ограниченный кэш опубликованного содержимого: ключ — `lesson_version_id`, TTL — 10 минут, максимум 32 версии и 16 MiB приблизительной оценки памяти, LRU-вытеснение и объединение одновременных cold-load запросов.
- Ответы, прогресс, история попыток и другие персональные данные не кэшируются. Draft-версии загружаются отдельным некэшируемым методом.

## Почему кэш безопасен

PostgreSQL-триггеры из начальной миграции запрещают менять и удалять опубликованные/архивные версии, запрещают изменять вопросы и их связанные материалы вне draft-версии и защищают библейские отрывки, на которые уже ссылается содержимое. Публикация новой редакции создаёт новый `lesson_version_id`. Следовательно, данные опубликованной версии можно безопасно адресовать по `lesson_version_id`; переход опубликованной версии в archived не меняет её содержимое.

Кэш имеет жёсткие ограничения по числу записей, приблизительному объёму и времени жизни. Слишком крупная версия не кэшируется. Значения и вложенные срезы/указатели копируются при чтении, поэтому вызывающий код не может изменить общий снимок.

## Сравнение SQL-пути

Сравнение ниже — статический подсчёт обращений по исходному коду для обычного callback перехода в активном курсе. Он не является измерением реального времени PostgreSQL/Telegram и не включает одинаковые для обоих вариантов сетевые операции Telegram и регистрацию ученика.

| Участок навигации | До оптимизации | После оптимизации |
| --- | ---: | ---: |
| Проверка активного ученика | 3 повторных проверки | 1 |
| Чтение прогресса | 3 раза (callback, navigate, OpenQuestion) | 1 |
| Проверка enrollment / course run | отдельное чтение enrollment + 2 чтения запуска курса/урока | одна проверка запуска и состава курса |
| Полная версия вопросов | до 3 полных загрузок с JSONB-агрегациями | 0 SQL при прогретом кэше; 1 SQL при cold load |
| Сохранение позиции | 1 без compare-and-set | 1 атомарный compare-and-set |
| Сохранённый ответ и история | 2 запроса | 2 запроса |
| Метаданные урока | `GetLessonDetail` + все вопросы | один `GetLesson` без вопросов |

Для штатного перехода с прогретым кэшем получается ориентировочно 7 SQL-команд навигации/рендеринга вместо порядка 17 по старому пути (не считая одинаковых запросов callback-регистрации). На холодном кэше добавляется одна загрузка версии, то есть ориентир — 8. Для legacy-прохождения без запуска курса запросов меньше в обоих вариантах. Реальное число команд следует подтвердить SQL-счётчиком на одном и том же сценарии и конфигурации.

## Сравнение времени

Достоверных значений p50/p95 «до/после» пока нет: диагностический PR #24 с агрегированными логами `telegram.update.process` остаётся отдельным открытым PR и не входит в текущий `main`. Кроме того, до запуска оптимизированной ветки на том же окружении нельзя приписать задержку только изменению кода.

После включения диагностики сравнивать на одинаковом окружении и наборе сценариев:
- `duration_ms` полного callback update, отдельно от long polling `getUpdates`;
- `sql.count` и `sql.duration_ms` для update;
- задержку получения соединения пула;
- отдельно холодное открытие версии и переходы по прогретому кэшу.

Для сравнения использовать не менее 100 переходов «Далее/Назад» до и после, одинаковое число пользователей и одинаковое состояние PostgreSQL; публиковать p50 и p95, а не единичный лучший замер.

# Этап 7.1. Аудит и подготовка измерений

Дата аудита: 2026-11-04  
Репозиторий: `Quantum103/Telegramm-Bot`  
Зафиксированный baseline: `fa175608dce22adfee3119af55ca6d2425a08c26` (`main`)  
Рабочая ветка аудита: `feature/stage-7-final-audit`

## 1. Вывод

Проект уже содержит оптимизации Telegram update pipeline и несколько целевых benchmark-тестов. Однако текущий набор тестов пока не позволяет достоверно ответить на вопросы о производительности полного пользовательского сценария под нагрузкой 1/5/10 учеников.

В частности, сейчас нет собираемых по операциям p50/p95/p99, длительности каждого вызова Telegram Bot API, регулярных снимков состояния pgxpool и измерений CPU/RAM backend во время нагрузки. Эти показатели нельзя восстановить из одного только успешного статуса CI.

На этапе 7.1 производственные обработчики не менялись. Этот документ фиксирует состояние baseline и методику, которую нужно использовать на следующих подэтапах.

## 3. Текущие настройки производительности

Значения по конфигурации и `.env.example` (это настройки по умолчанию, не результаты нагрузочного теста):

| Параметр | Значение по умолчанию |
|---|---:|
| PostgreSQL `DATABASE_MAX_CONNS` | 10 |
| PostgreSQL `DATABASE_MIN_CONNS` | 1 |
| Telegram update workers | 4 при пуле БД из 10 соединений |
| Очередь на одного Telegram worker | 16 updates |
| Теоретическая суммарная ёмкость очередей | 64 updates |
| Redis PoolSize | 16 |
| Telegram long polling | 30 секунд |
| Timeout обычного Telegram API вызова | 10 секунд |
| Timeout `answerCallbackQuery` | 3 секунды |
| Дополнительный запас для long polling HTTP request | 5 секунд |

Количество Telegram workers по умолчанию вычисляется как половина `DATABASE_MAX_CONNS`, но ограничено максимумом 4. Очереди разделены по chat key: updates одного чата направляются в одну FIFO-очередь. Поэтому суммарная ёмкость 64 не означает, что один горячий чат может занять все очереди; очередь конкретного worker может заполниться раньше, что приведёт к backpressure в polling loop.

В `HTTPClient.call()` уже есть контекстные дедлайны для Telegram API. Они ограничивают длительность вызова, но сами по себе не собирают статистику фактической длительности.

## 4. Уже существующие измерения

### 4.1. Telegram worker pool

Тест: `backend/internal/telegrambot/worker_pool_run_test.go`  
Benchmark: `BenchmarkUpdateWorkerPoolParallel`

- 4 workers и 16 элементов очереди на worker.
- Handler возвращает успех без выполнения бизнес-логики и SQL.
- Используется параллельная отправка задач.
- Go benchmark выводит среднее `ns/op` и аллокации.

Ограничение: это benchmark механизма очередей, а не нагрузочный сценарий полного бота. Он не измеряет PostgreSQL, Telegram API, каталог, открытие вопросов, ответы учеников или CPU/RAM Docker-контейнера.

### 4.2. Навигация между вопросами

Тест: `backend/internal/repository/question_navigation_benchmark_test.go`  
Benchmark: `BenchmarkQuestionNavigationPaths`

Сравниваются два пути на одном PostgreSQL fixture:

- `before` — реконструированная прежняя последовательность чтений, проверок и сохранения позиции.
- `after_warm_cache` — оптимизированная навигация с атомарным изменением позиции и прогретым кэшем опубликованных вопросов.

Измеряются `ns/op`, аллокации и SQL-команды на операцию (`sql/op`). Для запуска требуется `TEST_DATABASE_URL`.

Ограничения:

- это целевой benchmark одного перехода, а не сценарий одновременной работы 1/5/10 учеников;
- сравнение выполняется в одном benchmark-запуске, но только для навигации между вопросами;
- `after_warm_cache` не представляет холодный cache miss;
- средний `ns/op` не является p50/p95/p99.

### 4.3. Выход ученика в каталог

Тест: `backend/internal/repository/student_interaction_benchmark_test.go`.

Тест `TestLeaveStudentInteractionUsesOneSQLStatement` проверяет SQL tracing:

- прежний путь — 3 SQL-команды;
- объединённая операция `LeaveStudentInteraction` — 1 SQL-команда.

Последний успешный CI выполнил этот тест. Это подтверждает сокращение числа SQL-команд в данном конкретном пути с 3 до 1 (на 66,7%). Это не означает сокращение общей задержки на 66,7%: время выполнения и сетевые задержки отдельно этим утверждением не измеряются.

Benchmark сравнивает `ns/op`, аллокации и `sql/op`. Для полного пользовательского сценария этого недостаточно.

## 6. Обнаруженные пробелы в наблюдаемости

В исходниках baseline и зависимостях backend не обнаружен действующий Prometheus/OpenTelemetry endpoint или отдельная система сбора метрик. Также не найдено использования `pgxpool.Pool.Stat()` для регулярной фиксации состояния пула.

| Требуемый показатель | Что есть сейчас | Что потребуется для итогового аудита |
|---|---|---|
| p50 / p95 / p99 | Не собираются | Сохранять длительность каждой операции и рассчитывать процентили |
| Ошибки операций | Ошибки и категории ошибок логируются в отдельных местах | Единый счётчик операций и ошибок по сценариям |
| SQL-команды | Есть pgx tracer в отдельных benchmark-тестах | Включить подсчёт SQL для всех нагрузочных сценариев |
| Длительность SQL | В benchmark tracer считается количество запросов, но не распределение длительности | Замер длительности каждого SQL-запроса |
| Время Telegram API | Есть request timeout и классификация ошибок | Измерять каждое HTTP обращение отдельно |
| Состояние pgxpool | Настроены MaxConns/MinConns; регулярные метрики не найдены | Снимать Stat() и разницу счётчиков во время нагрузки |
| CPU backend | В тестах не собирается | Снимать метрики контейнера во время теста |
| RAM backend | В тестах не собирается | Снимать метрики контейнера во время теста |
| Очереди updates | Известна конфигурационная ёмкость | Фиксировать текущую глубину, ожидание Submit и отказы/блокировки |
| Восстановление после сбоев | Есть retry/backoff для long polling и delivery worker | Проверять временем и счётчиками в управляемом сценарии |

Отсутствие найденного endpoint не означает, что Go или Docker не позволяют получить такие данные. Это означает, что проект пока не сохраняет их как воспроизводимую метрику приложения.

## 7. Методика нагрузочных измерений для этапа 7.3

### 7.1. Изолированное окружение

- Использовать отдельную тестовую базу PostgreSQL, не базу с данными учеников.
- Применять все 15 миграций к пустой тестовой базе.
- Использовать отдельный Redis.
- Не отправлять тестовые сообщения реальным пользователям.
- Для Telegram Bot API использовать контролируемый fake HTTP API/transport с возможностью задавать задержки, timeout, HTTP 5xx и 429.
- Для внешнего источника Библии использовать управляемый тестовый HTTP transport.
- Для повышенной задержки PostgreSQL использовать отдельную тестовую сетевую прокси (например, Toxiproxy), не меняя production Compose.

### 7.2. Профили нагрузки

Каждый профиль запускать отдельно, с одинаковыми исходными данными и настройками:

1. 1 активный ученик.
2. 5 одновременно активных учеников.
3. 10 одновременно активных учеников.
4. Быстрые повторные нажатия на навигацию и ответы.
5. Повторная доставка одного и того же update.
6. Telegram API: обычная задержка, timeout, 5xx и 429.
7. Источник Библии: timeout, 5xx и восстановление.
8. PostgreSQL: штатная работа и контролируемая дополнительная задержка.

Для каждого запуска фиксировать commit SHA, параметры пула, число виртуальных учеников, число операций и длительность. Перед измерением выполнять прогрев. Для каждого профиля проводить минимум три повторения; для p99 стремиться собрать не менее 10 000 измерений на сравниваемую операцию, а при меньшей выборке явно указывать её размер.

### 7.3. Определения метрик

- **Latency операции:** время от передачи update обработчику до завершения бизнес-обработки. Отправку ответа в Telegram измерять отдельно, чтобы не смешивать внутреннюю обработку и внешнюю сеть.
- **Telegram API latency:** время каждого HTTP запроса от начала `Do` до чтения и разбора ответа.
- **SQL count:** количество завершённых SQL-команд на одну бизнес-операцию, через pgx query tracing.
- **SQL latency:** длительность каждого SQL вызова, измеренная в tracer.
- **Pool state:** снимать `pgxpool.Stat()` с фиксированным интервалом, включая acquired/idle/total/max connections и дельты acquire counters.
- **CPU/RAM:** снимать метрики именно backend-контейнера, например `docker stats`, с интервалом 1 секунда.
- **p50/p95/p99:** считать по массиву индивидуальных длительностей, а не выводить из среднего Go benchmark.
- **Errors:** учитывать все операции, в том числе timeout, повторные попытки и неуспешную доставку; разделять бизнес-ошибки и инфраструктурные ошибки.

Для каждого сценария сохранять исходные измерения (JSON/CSV), а не только сводную таблицу. Это позволит пересчитать процентили и проверить отчёт.

### 7.4. Сравнение до/после

Зафиксированный baseline до дальнейших изменений: `fa175608dce22adfee3119af55ca6d2425a08c26`.

Для каждого пути, где возможно, сравнивать baseline и финальный commit на одной версии Go, одинаковом Docker/Compose окружении, одинаковом числе соединений, одинаковом тестовом наборе данных и одинаковом сценарии нагрузки.

Для операций, где прежняя реализация уже воспроизведена внутри benchmark (навигация и выход в каталог), использовать этот парный benchmark и дополнять его полным сценарием. Для остальных операций не заполнять колонку «До» предположениями: сначала необходимо получить измерение на baseline SHA.

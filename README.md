# Библейская обучающая платформа

Платформа включает Telegram-бота с сохранением учебных ответов и прогресса, публичный каталог опубликованных уроков, защищённую веб-панель для авторинга/DOCX-импорта, управление сотрудниками и назначение кураторов. Автоматическая ИИ-проверка ответов и полноценный чат ученика с куратором пока не реализованы; требования к передаче в production и текущие ограничения описаны в `docs/security-audit.md`.

## Технологии

- Go 1.27 и стандартный `net/http`;
- PostgreSQL 18;
- `github.com/jackc/pgx/v5` и существующий пул `pgxpool`;
- React + TypeScript + Vite;
- Docker Compose v2;
- SQL-миграции с `golang-migrate` в отдельном контейнере.

## Требования

Для локального запуска нужны Docker Engine и Docker Compose v2 (или Docker Desktop для Windows). Чтобы запускать Go-тесты непосредственно на компьютере, нужен Go 1.27 или новее.

## Подготовка окружения

Создай локальный файл `.env` из примера.

Linux / macOS:

```bash
cp .env.example .env
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env
notepad .env
```

Измени `POSTGRES_PASSWORD` на локальный пароль. Не публикуй `.env` и не храни реальные секреты в Git: файл игнорируется через `.gitignore`. Для запуска Telegram-бота укажи `TELEGRAM_BOT_TOKEN` из `@BotFather`; если значение пустое, бот отключён, а HTTP API продолжает работать.

Если пароль содержит зарезервированные символы URI (например, `@`, `:`, `/`, `?` или `#`), укажи в `MIGRATIONS_DATABASE_URL` отдельный URI подключения с percent-encoded паролем. Пример формы URI:

```text
postgres://bible_app:URL_ENCODED_PASSWORD@postgres:5432/bible_platform?sslmode=disable
```

Если `MIGRATIONS_DATABASE_URL` пуст, Compose собирает адрес мигратора из `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB`. Для примера из `.env.example` этого достаточно.

## Запуск проекта и миграции

Миграции **не запускаются автоматически при старте API**. Это сделано намеренно: приложение не должно неожиданно менять или пересоздавать пользовательские таблицы при каждом запуске.

Обновление схемы включает миграцию `000005_staff_management`. На существующей БД сначала сделай резервную копию, затем примени все новые миграции. Миграция завершается ошибкой, если найдёт email сотрудников, совпадающие без учёта регистра: это намеренная защита от неоднозначного входа; сначала вручную разберись с дубликатами.

Сначала подними PostgreSQL:

```bash
docker compose up -d postgres
docker compose ps
```

На чистой базе примени версионируемые миграции отдельной командой:

```bash
docker compose --profile tools run --rm migrate
```

После успешной миграции собери и запусти приложение:

```bash
docker compose up --build -d
```

### Первый вход администратора

При старте backend проверяет наличие активного администратора и создаёт начальную учётную запись только при его отсутствии. По умолчанию email — `admin@localhost.test`, а криптографически случайный пароль генерируется автоматически и показывается один раз в логах backend:

```powershell
docker compose logs --tail=100 backend
```

Найди запись с полем `initial_password`, сохрани значение пароля и войди на <http://localhost:8081> → **Импорт DOCX**. При желании можно заранее задать `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD` в локальном `.env`; заданный пароль должен содержать не менее 12 символов и не выводится в логи. Не публикуй логи с начальным паролем. Этот bootstrap рассчитан на локальную разработку; не используй его по умолчанию в открытом production-окружении.

Открой:

- frontend: <http://localhost:8081>;
- backend: <http://localhost:8080>;
- readiness API: <http://localhost:8080/health/ready>;
- liveness API: <http://localhost:8080/health/live>.

При повторном запуске мигратора уже применённые версии пропускаются. Не запускай `down` или `down -v` для обычного обновления приложения.

### Изменение схемы в будущем

Добавляй новую пару файлов с последовательным номером, например `000002_add_example.up.sql` и `000002_add_example.down.sql`, в `backend/db/migrations/`. Прежде чем применять миграцию к базе с данными, проверь её SQL и возможные блокировки.

Для рабочих окружений предпочитай расширяющие миграции в несколько шагов: сначала добавить совместимые столбцы или таблицы, затем развернуть код, заполнить существующие данные и только после этого удалять устаревшие элементы отдельным согласованным изменением. Не редактируй уже опубликованные миграции, которые могли быть применены в чужом окружении.

Первая миграция создаёт всю начальную схему; её `.down.sql` удаляет эти таблицы и данные. Откат этой миграции допустим только для одноразовой разработки или тестовой базы после проверки содержимого. Он **не является безопасным способом отката production-базы**.

## Что хранится в PostgreSQL

### Ученики и сотрудники

- `students` — внутренний ID, уникальный Telegram ID формата BIGINT, отображаемое и предпочитаемое имя, username, статус и даты активности.
- `staff_accounts`, `staff_roles`, `staff_role_assignments` — отдельные записи сотрудников, роли administrator/curator и история назначения ролей. При первом старте backend автоматически создаёт первоначального администратора, если в базе ещё нет активного администратора; публичной регистрации сотрудников нет.
- `student_curator_assignments` — активное назначение куратора ученику с историей завершённых назначений.

Telegram username не используется в качестве постоянного идентификатора. `preferred_name` отделяет имя для общения от технического профиля.

### Курсы и содержимое уроков

- `courses`, `lessons`, `course_lessons` — курсы, самостоятельные уроки и порядок уроков в курсе.
- `lesson_versions` — версия содержимого урока с номером и состоянием draft/published/archived.
- `lesson_questions` — вопросы и исходные предполагаемые ответы по порядку.
- `question_options`, `question_criteria`, `question_common_mistakes` — варианты выбора, расширяемые критерии смысловой оценки и пояснения типовых ошибок.
- `bible_passages`, `question_bible_passages` — отрывки с названием книги, главой, диапазоном стихов, необязательным названием перевода и необязательным текстом. Конкретный перевод не навязывается схемой.

Содержимое прохождения фиксируется на `lesson_version_id`, поэтому правки опубликованного урока следует выпускать новой версией. SQL-триггеры блокируют изменение или удаление опубликованных/архивных вопросов, критериев, вариантов и связанных библейских отрывков. Новые прохождения начинаются только по текущей опубликованной версии; уже начатое прохождение продолжает ссылаться на свою архивную версию и может восстановить её содержимое. Создай новую draft-версию для правок.

### Прогресс, ответы и попытки

- `lesson_enrollments` — прохождение ученика по конкретной версии урока, режим ai/curator, текущий вопрос, состояние и временные отметки.
- `student_answers` — текущий сохранённый ответ ученика на вопрос; он нужен для восстановления ответа при возврате к предыдущему вопросу.
- `answer_attempts` — неизменяемая по смыслу история отправок и проверок, включая снимок отправленного текста, идемпотентный ключ, статус обработки, результат, пояснение, отсутствующие пункты, провайдера/модель и длительность.
- `student_answer_options` и `answer_attempt_options` — выбранные варианты для вопросов с выбором ответа.

Технические состояния попытки (`pending`, `running`, `completed`, `failed`) отделены от результата оценки (`correct`, `partial`, `incorrect`, `ambiguous`). Сбой сервиса ИИ фиксируется как `failed` с кодом ошибки и не превращается в неправильный ответ. Сохранение текущего ответа, записи попытки и обновление прогресса выполняются одной транзакцией. Повтор запроса с тем же UUID в рамках прохождения не создаёт ещё одну попытку.

### Диалоги, расходы ИИ и аудит

- `conversations`, `conversation_participants`, `conversation_messages`, `conversation_message_reads` — внутренние диалоги, участники, история сообщений, метки прочтения и Telegram ID сообщения при наличии.
- `conversation_messages` хранит текст либо метаданные вложения. Для голосовых сообщений сохраняется Telegram `file_id`; скачивание аудиофайлов схемой не требуется.
- `ai_operations` — провайдер, модель, вид операции, статус, доступные данные о токенах, стоимости и длительности. API-ключи туда не сохраняются.
- `audit_events` — журнал значимых действий с типом сущности и безопасными JSON-деталями; записываемые детали не должны содержать токены, пароли или API-ключи.

Часть схемы по-прежнему резервирует будущие функции: автоматическую ИИ-интеграцию и отправку сообщений в диалоге с куратором. Управление сотрудниками, назначениями кураторов и списком учеников реализовано в защищённом административном API; записи в `conversations` обновляются при переводе ученика к другому куратору.

## Слой доступа к данным

Репозитории расположены в `backend/internal/repository/` и используют тот же `*pgxpool.Pool`, который создаётся существующим компонентом `backend/internal/database`:

- `StudentRepository` — создание ученика, поиск по внутреннему ID и Telegram ID, идемпотентный upsert и обновление профиля;
- `ContentRepository` — получение текущих опубликованных уроков курса и содержимого конкретной опубликованной/архивной версии: вопросов, критериев, вариантов, типовых ошибок и связанных библейских отрывков;
- `AnswerRepository` — атомарная отправка текста или выбранных вариантов, чтение сохранённого ответа и истории, запись результата оценки или технической ошибки.

Все операции принимают `context.Context` и используют параметризованные запросы. Каталог, авторинг, аутентификация сотрудника, управление сотрудниками и кураторскими назначениями подключены через HTTP API. Отдельный публичный HTTP API для выполнения уроков от имени произвольного ученика не предоставляется.

## Доменная логика третьего этапа

Бизнес-логика размещена в `backend/internal/domain` и `backend/internal/service`. Она не зависит от Telegram Bot API и внешнего ИИ.

- `StudentService` — идемпотентное создание/обновление профиля по Telegram ID, получение по внутреннему ID и обновление пользовательских полей.
- `CatalogService` — чтение опубликованных курсов, уроков и учебных материалов.
- `AuthoringService` — внутреннее создание черновых курсов, уроков и вопросов, публикация, а также клонирование опубликованного урока в новую draft-версию с вариантами, критериями, распространёнными ошибками и ссылками на библейские отрывки. Сервис не подключён к публичным write-endpoints и предназначен для будущей защищённой панели/импортёра.
- `LearningService` — начало и восстановление прохождения, навигация по вопросам, возврат сохранённого ответа и последней попытки, валидация отправки и явное завершение урока.
- `CatalogRepository` — SQL-запросы каталога с сортировкой уроков по `course_lessons.position`, проверкой принадлежности урока курсу и вопросов по `question_number`.
- `EnrollmentRepository` и `AnswerRepository` — сохранение позиции и расчёт прогресса, транзакционное сохранение текста или выбранных вариантов, история попыток и идемпотентная обработка повторов.

Завершение прохождения не происходит при открытии последнего вопроса и не означает, что ответы признаны правильными: явная операция завершения доступна только тогда, когда в базе сохранён ответ на каждый вопрос. Новая отправка ответа создаёт отдельную попытку, не стирая историю. Пока ИИ-проверка не реализована, новая попытка получает статус `pending`, а результат оценки остаётся `NULL`.

### Доступные безопасные GET-маршруты

Все пути относятся к локальному backend на `http://localhost:8080`.

Получить опубликованные курсы:

```http
GET /api/v1/courses
```

Пример успешного ответа:

```json
{
  "courses": [
    {
      "id": 1,
      "slug": "sample-course",
      "title": "Название опубликованного курса",
      "lesson_count": 3
    }
  ]
}
```

Получить конкретный опубликованный курс:

```http
GET /api/v1/courses/1
```

Получить уроки курса в сохранённом порядке:

```http
GET /api/v1/courses/1/lessons
```

Получить опубликованный урок и его вопросы:

```http
GET /api/v1/lessons/10
```

Получить урок в контексте конкретного курса (маршрут дополнительно проверяет связь `course_lessons`):

```http
GET /api/v1/courses/1/lessons/10
```

Ученический ответ содержит текст вопроса, тип ответа, варианты без признака правильности и связанные библейские ссылки/текст отрывка, если он был сохранён. Предполагаемый ответ, критерии ИИ, пояснения и типичные ошибки в этих DTO намеренно исключены.

Некорректный ID возвращает `400` с кодом `invalid_id`, отсутствующий или непубликованный ресурс — `404` с кодом `not_found`, а внутренняя ошибка — `500` с общим кодом `internal_error`, без SQL и подробностей БД. Публичный API не позволяет менять прогресс или отправлять ответы от имени произвольного ученика. Административные операции защищены серверными сессиями, CSRF-проверкой, проверкой Origin и RBAC.

### Миграция третьего этапа

`backend/db/migrations/000002_answer_uncertain_result.up.sql` расширяет допустимые результаты оценки, добавляя `uncertain`, сохраняя совместимость с прежним значением `ambiguous`. Существующие миграции не изменялись.

На существующей базе с уже применённой схемой обновление выполняется той же командой:

```bash
docker compose --profile tools run --rm migrate
```

Откат `000002` преобразует `uncertain` в прежнее значение `ambiguous`, после чего восстанавливает старое ограничение. Сама схема третьего этапа не выполняет автоматической ИИ-проверки.

## Telegram-бот: подэтап 4.1

Бот использует long polling Telegram Bot API через стандартные пакеты Go; отдельная Telegram-библиотека не требуется. В PostgreSQL ученик регистрируется через StudentService.EnsureByTelegramID, который использует Telegram ID как стабильный ключ и не создаёт дубликат при повторном /start. Подэтап 4.2 добавляет каталог курсов, опубликованные уроки и навигацию по вопросам через inline-клавиатуру.

### Получение токена

1. Открой официальный аккаунт @BotFather в Telegram.
2. Отправь команду /newbot, выбери отображаемое имя и уникальный username бота.
3. Сохрани выданный токен локально. Не отправляй его в чаты, issues, коммиты или логи.

В локальном .env, созданном из .env.example, впиши токен:

```dotenv
TELEGRAM_BOT_TOKEN=токен_от_BotFather
```

Не меняй .env.example, чтобы добавить настоящий секрет. Эта переменная передаётся только backend-контейнеру и не публикуется во frontend.

### Запуск и проверка

Из корневой папки проекта выполни:

```bash
docker compose up -d postgres
docker compose --profile tools run --rm migrate
docker compose up --build -d
docker compose ps
docker compose logs -f backend
```

Открой созданного бота в Telegram и отправь /start. При успешном подключении в логах backend появляется запись «Telegram-бот авторизован» с Telegram ID и username бота (токен не выводится). Бот отвечает приветствием после успешного поиска/создания ученика в PostgreSQL. Проверь также /help и /cancel.

Если TELEGRAM_BOT_TOKEN пуст, в логах будет явно указано, что бот отключён; HTTP API продолжит работать. При ошибке авторизации проверь токен в .env и перезапусти backend: docker compose up -d --force-recreate backend. Если видишь конфликт getUpdates / HTTP 409, останови другой экземпляр приложения, использующий тот же токен. При временных сетевых ошибках polling повторяется с увеличивающейся задержкой; остановка контейнера через Docker завершает polling вместе с HTTP-сервером.

Автоматические тесты не используют настоящий токен и не отправляют сообщения реальному Telegram. Реальное подключение проверяется только после запуска backend с выданным токеном и проверки приветствия в самом Telegram.

### Каталог и навигация по урокам (подэтап 4.2)

После /start бот показывает опубликованные курсы. Выбери курс, затем урок: экран вопроса содержит название урока, номер вопроса и кнопки «Назад», «Далее» и «К урокам». Во время обычной навигации основное сообщение редактируется; если Telegram больше не позволяет его редактировать, бот отправит замену. Номер текущего вопроса сохраняется в существующей записи прохождения PostgreSQL, поэтому после перезапуска можно снова открыть тот же курс и урок, чтобы восстановить позицию. Подэтап 4.3 подключает приём учебных ответов: свободный текст и варианты сохраняются через LearningService и PostgreSQL, а история попыток остаётся доступной.

### Учебные ответы (подэтап 4.3)

- Для вопроса типа \`text\` отправьте ответ отдельным сообщением. Пустые сообщения и команды не сохраняются как учебные ответы.
- Для \`single_choice\` выберите один вариант кнопкой. Для \`multiple_choice\` отметьте нужные варианты и нажмите «Подтвердить выбор».
- Ученик, активное прохождение, текущий вопрос и принадлежность вариантов повторно проверяются доменным сервисом. Текущее значение ответа, история попыток, выбранные варианты и прогресс сохраняются существующей транзакционной реализацией.
- Один Telegram update получает детерминированный UUID idempotency key. Повторная доставка той же отправки не создаёт вторую попытку; новый update при изменении ответа сохраняет новую попытку.
- После успешной записи бот пытается удалить исходное текстовое сообщение ученика. Ошибка удаления не отменяет ответ. Если сохранение не прошло, исходное сообщение остаётся и ученик получает безопасную инструкцию повторить отправку.
- Пока ИИ-проверка не реализована, попытка имеет статус \`pending\`, результат оценки остаётся пустым, а бот не выдаёт оценку «правильно/неправильно» и не раскрывает предполагаемый ответ или критерии.

## Health endpoint, логи и остановка

- `GET /health/live` возвращает HTTP 200, если процесс отвечает.
- `GET /health/ready` возвращает HTTP 200, если PostgreSQL доступен, или HTTP 503 без подробностей внутренней ошибки.

Логи:

```bash
docker compose logs -f
docker compose logs -f backend
docker compose ps
```

Остановить контейнеры, сохранив данные PostgreSQL:

```bash
docker compose down
```

Удалить контейнеры вместе с именованным томом PostgreSQL:

```bash
docker compose down -v
```

Последняя команда удаляет данные базы. Выполняй её только тогда, когда уверен, что том можно уничтожить или у тебя есть резервная копия. PostgreSQL хранит данные в именованном томе `postgres_data`, смонтированном в `/var/lib/postgresql`.

## Тестирование

Unit-тесты и статические проверки миграций выполняются из каталога backend:

```bash
cd backend
gofmt -w ./cmd ./internal
go test ./...
```

Если `TEST_DATABASE_URL` не задан, интеграционные тесты пропускаются. Для них нужна отдельная тестовая PostgreSQL-база с уже применёнными миграциями. **Тесты очищают `students`, `courses` и `lessons` с помощью `TRUNCATE ... CASCADE`, затрагивая связанные таблицы. Не запускай их на базе с пользовательскими данными или на основной локальной базе.**

Пример безопасного создания отдельной тестовой базы из корня проекта:

```bash
docker compose exec postgres createdb -U bible_app bible_platform_test
```

Временно укажи `MIGRATIONS_DATABASE_URL` в локальном `.env` на тестовую базу внутри Docker и примени миграции:

```text
postgres://bible_app:URL_ENCODED_PASSWORD@postgres:5432/bible_platform_test?sslmode=disable
```

```bash
docker compose --profile tools run --rm migrate
```

Затем запусти интеграционные тесты с URI для подключения с хоста. Linux / macOS:

```bash
cd backend
TEST_DATABASE_URL='postgres://bible_app:URL_ENCODED_PASSWORD@localhost:5432/bible_platform_test?sslmode=disable' go test ./...
```

Windows PowerShell:

```powershell
$env:TEST_DATABASE_URL = "postgres://bible_app:URL_ENCODED_PASSWORD@localhost:5432/bible_platform_test?sslmode=disable"
Set-Location backend
go test ./...
Remove-Item Env:TEST_DATABASE_URL
Set-Location ..
```

Если использовался временный `MIGRATIONS_DATABASE_URL`, верни его к пустому значению после тестирования.

## Ограничения текущего этапа

- Telegram-бот поддерживает `/start`, `/help`, `/cancel`, каталог опубликованных курсов и уроков, а также навигацию по вопросам. Приём и сохранение новых учебных ответов, ИИ-проверка, импорт DOCX/ZIP, бизнес-HTTP API и интерфейс управления остаются будущими этапами.
- Сотрудники и роли описаны схемой, но аутентификация, авторизация и ограничения доступа на уровне приложения ещё не реализованы.
- Первая миграция создаёт таблицы платформы с нуля; она рассчитана на пустую базу первого этапа. Если в существующей базе уже появились данные приложения, сначала сделай резервную копию и проверь состояние схемы.
- Запуск миграции является отдельным действием и не выполняется автоматически при старте backend.


## Управление сотрудниками и учениками

После применения миграций вход остаётся закрытым для публичной регистрации. Администратор может создать сотрудника с ролью `administrator` или `curator`. Backend генерирует криптографически случайный временный пароль, сохраняет только PBKDF2-хеш и возвращает временный пароль только в ответе создания/сброса. Не сохраняй ответ в тикеты или общие чаты: передай пароль сотруднику лично. До смены пароля сервер разрешает только проверку сессии, смену пароля и выход. После смены пароля активные сессии сотрудника отзываются.

В панели раздел **Ученики** показывает статус и сводный прогресс по прохождениям. Администратор может назначить куратора, перевести ученика другому куратору или завершить назначение. История хранится в `student_curator_assignments`; обновление активных назначений и связанных активных диалогов выполняется транзакционно. Куратор получает только строки назначенных ему учеников: это серверное ограничение БД-запроса, а не просто фильтр интерфейса.

### Новые административные маршруты

Все маршруты ниже требуют активную staff-сессию; небезопасные методы также требуют Origin и CSRF. Изменения доступны только администратору.

| Метод и маршрут | Назначение |
|---|---|
| `GET /api/v1/staff/admin/staff` | Список сотрудников и ролей |
| `POST /api/v1/staff/admin/staff` | Создать сотрудника, вернуть временный пароль один раз |
| `PATCH /api/v1/staff/admin/staff/{staffID}/status` | Активировать/отключить сотрудника; активные сессии отзываются |
| `POST /api/v1/staff/admin/staff/{staffID}/reset-password` | Выдать новый временный пароль; требуется обязательная смена |
| `GET /api/v1/staff/admin/students` | Список учеников и сводный прогресс; куратор видит только назначенных ему |
| `PUT /api/v1/staff/admin/students/{studentID}/curator` | Назначить или перевести ученика к куратору |
| `DELETE /api/v1/staff/admin/students/{studentID}/curator` | Завершить активное назначение |

Смена роли сотрудника также отзывает его действующие сессии. Нельзя отключить собственную учётную запись, изменить собственный набор ролей через соответствующие маршруты или деактивировать последнего активного администратора. Критические изменения записываются в `audit_events`.

### Текущие ограничения безопасности

MFA/2FA пока не реализована. **Не публикуй панель в открытый production и не считай проект production-ready до внедрения MFA и независимого security review.** Также пока нет автоматической ИИ-проверки ответов, рабочего сценария диалогов/сообщений между учеником и куратором, frontend unit/e2e-тестов и процесса безопасного восстановления через внешний канал. Полный список подтверждённых контролей и ограничений — в [`docs/security-audit.md`](docs/security-audit.md).
